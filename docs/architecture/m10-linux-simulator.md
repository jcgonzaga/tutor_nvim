# M10 — Linux simulator: architecture notes

Status: implemented and tested end to end (engine, schema, evaluation, session, terminal UI, API,
content). Product decisions taken: Linux practice is **mixed into the daily session with Vim**, and
the first Linux skill is **open from day one**. Design record: [ADR-0004](adr/0004-linux-simulator.md).

## The engine (`packages/shell-engine`)

A framework-free simulator of a small shell over an in-memory file system, validated against real
bash. Scope, design and what is not modelled: ADR-0004. In short: `pwd ls cd mkdir touch cp mv rm cat
echo chmod grep find wc head tail sort`, quoting, variables, globs, pipes, `; && ||`, redirections,
permissions, terminal key input with history.

```ts
let state = initShell({ files: { "project/src/app.js": "const API_URL = 1;\n" } });
state = typeCommand(state, "grep -r API_URL project");
state.transcript.at(-1)?.output; // "project/src/app.js:const API_URL = 1;\n"
```

The transcript keeps each line's exit status and the key presses spent on it, which is what the
evaluation needs to tell a command that failed from one that worked.

## Content model

`Exercise = VimExercise | ShellExercise`, told apart by `kind` (content without `kind` is Vim, so no
Vim file changed). A shell exercise has:

- `initialState`: `files` (a trailing `/` makes an empty folder), `modes` (octal, files only), `cwd`;
- `objective`: `fs_matches` (files with exact content, folders, absent paths, permissions),
  `cwd_equals`, `last_output_equals`, `last_output_contains`, and `all` of them. Paths are relative
  to home. The objective is only judged after a command runs, because that is when the state moves;
- `solutions`: lists of **commands**, expanded to the keys that type them plus Enter, so every
  declared solution is executed by the engine in CI (AGENTS.md section 10);
- shell anti-patterns: `repeated_failed_command`, `cd_up_chain`, `rm_rf_wildcard`.

## Evaluation

The two questions stay independent (AGENTS.md section 12): `success` from the goal, `strategy` from
declared solutions, anti-patterns and keystroke efficiency against the shortest optimal solution.
What is shell-specific:

- an **error** is a command that failed (non-zero exit) or a key the terminal ignored; the keys of a
  failed command count as wasted, so `accuracyScore` falls with them (a typo costs, but a run that
  recovers still solves it);
- anti-patterns read the commands the learner ran, and point at the key events that typed them;
- `Replay` is Vim-only for now (it draws the editor); the ghost comparison, the master's keys and the
  feedback work for both.

## Session and mastery

Nothing in mastery, scheduling, unlocking or XP changed: they were already keyed by skills and
contexts. Two changes in the session builder carry the product decisions:

- the **learn** block opens one skill **per domain** and alternates between them (Vim first on a tie,
  then whichever domain the learner has practiced least), so day one is Vim, shell, Vim. With one
  domain available it behaves as before;
- a new skill's exercises are offered in stage order (learn, imitate, recall...), then by difficulty.

Eight Linux skills (`linux.shell.navigation` is the root; `view`, `create`, `copy-move`, `remove`,
`search`, `permissions`, `pipes` unlock through it) and 48 exercises (6 per skill: learn, imitate, two
recall, discriminate, transfer), in five contexts. They meet the same quality gates as the Vim
curriculum: at least 5 exercises, 3 contexts, 3 stages and a transfer exercise per skill. They are
generated by `scripts/author/shell-gen.ts` from `shell-specs.ts`, which refuses to write an exercise
whose solutions do not reach its objective.

## API and persistence

The server replays a shell attempt with the same engine, exactly as for Vim (the client only sends
keys). Events keep their shape: `mode` is `shell` and the cursor columns are the caret in the typed
line, so a future ghost replay can rebuild the line. No schema change, no migration.

## Verification

- shell-engine: 44 oracle scenarios (268 lines) against real bash + 26 unit tests;
- exercise-schema and evaluation: shell cases for parsing, normalization, goals, strategy, metrics,
  feedback, anti-patterns and content checks;
- pedagogy: the two-domain learn block, deterministic;
- API: shell attempts replayed, stored and scored (also on real Postgres, 95 tests);
- E2E: typing, errors, Ctrl+C/Ctrl+U, history, anti-pattern feedback, hints, a first session with
  both kinds, the map; axe on the terminal and its result;
- performance: a terminal key reaches the screen in about 20 ms (p95) with a 40-entry transcript.

## Not done

- Replay of a shell run in the UI, and `less`, Tab completion, in-line cursor movement, `sed`/`awk`,
  symlinks and running scripts (ADR-0004).
- The calibration check is still Vim-only: a learner's shell level is found by practice.
- The Spanish/English copy question is unchanged: the app is in English.
